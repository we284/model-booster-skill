## 阶段 0：任务澄清

缺少以下任一信息且无法从上下文推断时，先问用户，不要带着假设开工：

- 输入输出形式（函数/命令行/服务/界面）、运行环境与版本、依赖约束
- 必须满足的非功能要求（性能、兼容性、编码、平台）
- 已有代码的约定（修改现有项目时先读项目结构和风格，匹配现有约定）

歧义不影响整体方向时可自行决定并注明，不把选择题全部抛给用户。

**前提校验**：用户对现状的描述（"这个函数没被调用""报错是因为依赖版本"）先用代码核实再动工——按用户说的错因修半天而错因不在，是最贵的返工。

## 阶段 1：规格与计划

先输出实现规格，再写代码：

1. 功能点清单，逐条对应用户需求。
2. 函数/模块划分：每个单元的职责、输入、输出、异常行为。
3. 边界条件清单：空输入、零值、极大值、重复值、并发、文件不存在、权限不足、编码异常。
4. 风险点：可能出错的算法、依赖、平台差异。
5. 验证计划：用什么测试和命令证明正确。

## 阶段 2：测试先行

先写测试再写实现（修改现有代码时先补能复现问题的失败测试）：

- 正常路径：典型输入的正确输出。
- 边界路径：空、单元素、首尾、最大值、类型边界。
- 异常路径：非法输入的预期行为（报错信息或约定返回值），禁止静默吞错。
- 测试必须可独立运行，断言具体值而非"不报错即可"。

## 阶段 3：分步实现

1. 按模块小步实现，每完成一个单元立即运行对应测试，保持全程可运行状态。
2. 复用成熟库，不重复造轮子；不确定的 API 行为写最小验证脚本实测，不靠记忆。
3. 错误处理覆盖真实失败点；资源（文件、连接、进程）用上下文管理器或显式关闭。
4. 命名表达意图，函数短小职责单一；注释解释"为什么"，不复述"是什么"。

## 阶段 4：真实运行验证（不可跳过）

1. 运行全部测试，保存真实输出。
2. 有 lint/类型检查工具时运行并处理全部 warning。
3. 做一次端到端 smoke test：用真实场景数据走完整路径。
4. 修 bug 时先确认测试能复现，修复后确认测试转绿，再检查同类问题。
5. 任何"在我机器上应该没问题"的表述都不允许，证据只有真实运行输出。

## 调试协议（修 bug 时强制，覆盖阶段 3-4 的普通流程）

1. **先复现**：写出稳定复现的最小用例并运行确认它失败。复现不了就先查清复现条件，不开工。
2. **定位**：二分、日志、断点、最小复现逐步缩小范围；一次只改一个变量，别同时动三处猜哪处起效。
3. **根因**：对"为什么会出现这个行为"连续追问到系统性原因，修复落在根因上。禁止只压制症状：吞异常、加默认值兜底、放宽断言、改测试让红变绿都不是修复。
4. **红绿验证**：修复前测试红（已确认）；修复后转绿；再把修复回滚一次确认测试重新变红——证明测试真的打到了这个 bug，而不是碰巧同绿。
5. **回归**：全量测试 + 排查同一根因的其他表现位点（同文件同类代码、同调用链上下游）。

## 阶段 5：批判与修复循环

先跑下方"攻击测试模板"，再按 critique-rubrics.md 的代码清单逐项检查，每项给"通过/不通过+证据（测试输出或代码位置）"。不通过项修复后重跑全部测试。最多 3 轮，退出条件见 SKILL.md §6。

## 阶段 6：交付

交付内容必须包含：

- 可运行的代码文件和完整路径
- 运行命令、依赖和环境要求
- 测试方式与实际测试结果摘要
- 已知限制、未覆盖场景和后续建议

## 弱模型高频缺陷清单（实现和审查时主动排查）

- 差一错误：循环边界、切片索引、分页页码
- 可变默认参数、浅拷贝共享引用、全局状态污染
- 浮点直接判等；整数除法与取负行为；大整数溢出（跨语言）
- 字符串编码假设、未指定 encoding 打开文件、换行符差异
- 相对路径假设工作目录；硬编码分隔符；路径拼接不用专用库
- 捕获过宽异常后 pass；只打印不处理；丢失原始异常栈
- 症状修复：吞异常、默认值兜底、改断言/改测试让红变绿，根因原样留在原地
- 资源未关闭；子进程未等待；临时文件未清理
- 并发下的竞态、非线程安全集合、死锁
- 安全：命令注入、SQL 拼接、未校验输入、密钥硬编码、路径穿越
- 只处理 happy path，忽略网络/IO/权限失败
- 改代码不看调用方，破坏现有接口契约

## 攻击测试模板（阶段 5 必跑）

不用全部跑，按代码性质挑 3-4 项；但**必须真跑，不许脑内推演**。每项记录：输入 → 期望 → 实际。

| # | 攻击向量 | 具体做法 |
|---|---|---|
| A1 | 空与零 | `None`/`null`、空字符串、空列表、空文件、0 长度的切片 |
| A2 | 极值与规模 | 单元素、百万级元素、超长字符串、超大文件分块、整数上界附近 |
| A3 | 类型与编码 | 数字与字符串混入、UTF-8 BOM、CRLF 换行、路径含空格/中文/emoji |
| A4 | 失败注入 | 文件不存在、权限拒绝、网络超时、依赖返回 None、磁盘写满（用 mock 或临时目录模拟） |
| A5 | 重复与状态 | 同一函数连调两次结果是否一致（幂等）；上一次的全局状态是否污染下一次 |
| A6 | 索引边界 | 首元素、末元素、分页最后一页、区间闭开、负数索引 |
| A7 | 并发 | 两个请求同时写同一资源；加锁前后行为是否一致 |
| A8 | 真实数据 | 用用户真实样例跑一遍完整路径，不用自己造的小数据代替 |

回归测试额外要求：修 bug 前先写出**能失败的测试**并运行确认它红；修复后确认转绿。测试一直绿说明测试没打到 bug。

## 验证证据留存

1. 每条关键验证命令的输出保留关键几行，交付时引用原样行（如 `7 passed in 0.42s`），不要转述成"测试通过"。
2. 命令与结果配对写：`<命令> → <关键输出>`，便于用户复现。
3. 无法运行验证时（环境缺失、无权限），写"未执行"并给出用户可自行执行的完整命令，同时把相关结论降级为部分验证。
